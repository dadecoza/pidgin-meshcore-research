# External review: three confirmed issues

The review was supplied during development on 2026-10-30. No Git repository
existed then, so an exact vulnerable plugin commit is unavailable. All fixes
below are present in maintained plugin `fe078f29110a68f7ae326087ad2f8581d56130c3`; source behavior was
checked against MeshCore `81dbae592ffad40b4212bc0b37e82b38da08f4bc`.
The external reviewer reported source inspection but could not run tests in their
environment. The later local regression runs are separate evidence.

1. **High: queued binary channel datagram disconnected the session.** Firmware
   queues 0x1B datagrams with text. The plugin formerly accepted only empty/direct/
   channel-text replies to SYNC_NEXT_MESSAGE. Fix: validate nine-byte header,
   slot/path/declared body length, discard unsupported content, continue draining.
   Tests: `/core/queued-datagram`, `/core/malformed-datagram`.
2. **High: display names used as conversation identities.** libpurple identifies
   conversations by account and name. Duplicate configured channel names could
   reuse a conversation, replace its chat ID and redirect replies. Fix: use the
   session identity internally with a readable title; allocate fresh chat IDs;
   look up current conversations by identity, reject stale IDs after reconnect.
   Headless tests use duplicate names with different slots/keys and a replacement
   PTY, checking separate histories, reply slots and stale-send/leave rejection.
3. **Medium: final bytes discarded with hangup.** A readable callback could
   obtain bytes while also receiving HUP, then disconnect before parsing them.
   Fix: process complete frames before reporting terminal loss, continue bounded
   drain dispatches, suppress output watches during draining, and drain on write
   failure too. Tests: `/serial/final-frames-hangup`,
   `/core/final-message-hangup`, `/core/final-ack-hangup`. A socketpair retains
   final buffered bytes plus HUP; Linux PTYs can discard unread data on closure.

These are host/simulator regressions. No hardware reproduction of these three
edge cases is claimed. Later hardware reconnect observations verify only normal
USB initialization. See [publication results](../validation/PUBLICATION.md).
